The generator is wired to all **140 reviewed GLO-30 COGs**, keeping the original 137 source precedence. It does not select any new sources. It consumes a **prebuilt** genuine OpenStreetMap physical land polygon clip already defined by the [existing coastline preprocessing](../scripts/osm_land_reference.py), and a locally supplied OSM Colombia admin relation R120027 GeoJSON. It uses the **exact existing 256×256 XYZ pixel centers** and raster-native COG warping.

Each candidate tile is classified by positive masks:
- OSM physical land **AND** Colombia OSM relation: original GLO-30 elevation required.
- No physical Colombian land: **skip entirely**.
- Full physically Colombian OSM land: fail on any missing original native DEM height, encode precise Mapbox Terrain-RGB values in real PNG, validate round-trip to ±0.051 m, write TMS coordinates to a real SQLite MBTiles file.
- Mixed land/offland: **fail closed before writing**. Neither ocean RGB 0/0/0 nor 0 m artificial bathymetry can be silently inserted.

The generator uses an **atomic incomplete-file convention** and SQLite integrity checks. A failed pilot cannot leave a seemingly publishable partial MBTiles. No actual national native DEM, giant OSM archive or released user-visible MBTiles is generated by its offline CI test: the source heights and land geometry in the test are explicitly synthetic fixtures for verifying the engine, never factual Colombian elevation data.

### How to run when OSM land geometry and staging artifact are locally available

```bash
python scripts/generate_osm_land_only_terrain.py \
  --source-manifest output/stage140/colombia_dem_manifest_tumaco_staging_140.csv \
  --osm-land-clip output/osm-reference/osm-land-study.wkb.gz \
  --osm-land-meta output/osm-reference/osm-land-study-metadata.json \
  --osm-country-geojson output/osm-country/colombia-relation-120027.json \
  --bbox -75.65 6.23 -75.57 6.31 \
  --minzoom 11 --maxzoom 13 \
  --max-tiles 300 \
  --output output/colombia-inland-osm-land-safe-pilot.mbtiles
```

The Colombia relation JSON must have the documented fields `{"source":"OpenStreetMap","OSM_relation_id":120027,"geometry":{...}}` with the actual OSM R120027 geometry. It must be independently sourced, not hand-drawn or invented.

**Precondition:** These geometry inputs are not currently committed as large repository files. The previous 1 GB OSMCoastline scan kept provenance but did **not** retain the full binary clipped geometry as a durable reusable artifact. Do not claim the national generator is runnable end-to-end without supplying that existing input; when preparing nationwide output, create and cache a durable permitted clip to avoid repeatedly fetching OSM.

## Critical MapLibre raster-dem limitation

[MapLibre's DEMData implementation](https://github.com/maplibre/maplibre-gl-js/blob/main/src/data/dem_data.ts) unpacks only the **R, G and B** channels to numeric elevation, with no alpha/no-data mask in its elevation decoder. Therefore PNG transparency **cannot** be assumed to remove fake bathymetry from a mixed coast tile. An unmasked RGB 0/0/0 represents **−10,000 m**, which would produce a fictitious trench. A PNG alpha-zero pixel with RGB carrying a placeholder elevation is still numerically decoded.

For the user-defined scope, *sea depths are not required at all*. That does **not** yet solve how to encode pixels in a mixed coast tile for the **specific** MapLibre renderer. The current fail-closed generator is intentionally **inland-only**; national release must not silently omit coastal land. Before release, separately validate a renderer-safe coast convention and whether a strictly *render-only* ocean background is acceptable to the maintainer, or implement a mask-aware consumer.
